===========
arp_project
===========

기본 게이트웨이가 남의 하드웨어 주소로 넘어가는 것을 막는다.

3.10 커널의 jolla-kernel_bullhead 와 4.4 커널의 jolla-kernel_joan 에서
가져왔고, 영구 차단이 게이트웨이 자신을 향하지 않도록 다시 만들었다.

무엇을 막는가
=============

ARP 는 링크에 "이 주소 쓰는 사람 누구야?" 를 물어보고 주인이 "나야, 내
하드웨어 주소는 이거야" 하고 답하는 방식이다. 답을 검증하는 장치가 없다.

그래서 링크에 있는 무엇이든 게이트웨이보다 먼저, 또는 더 자주 답하면 ARP
테이블이 그쪽을 가리키게 되고, 이 컴퓨터에서 나가는 모든 것이 그곳을
거친다.

arp_project 는 게이트웨이의 하드웨어 주소를 못박아 두고 그것을 옮기려는
시도를 거부한다.

패킷 처리
=========

``net/ipv4/arp.c`` 의 ``arp_gw_check()`` 가 ARP 테이블을 바꿀 수 있는 모든
경로보다 먼저 실행된다::

  1) 이 장치의 기본 경로 게이트웨이 주소를 구한다   arp_gw_of()
  2) 이 패킷이 그 주소를 주장하나?
       아니오 -> 통과, 끝
  3) 보낸 하드웨어 주소가 차단 목록에 있나?
       예     -> 버린다, 끝
  4) arp_gw_claim() 으로 판정

``arp_gw_claim()``::

  보호 기록이 아직 없다
     ARP 테이블에 게이트웨이 주소가 있으면 -> 그것을 보호한다
     테이블이 비어 있으면                  -> 이 패킷이 넣으려는
                                              주소를 보호한다

  보낸 하드웨어 주소 == 보호 대상?
     예     -> 게이트웨이 자신이다. 통과
     아니오 -> 남이 사칭 중이다. 버리고 검증한다.

두 번째 경우가 중요하다. 테이블에서만 가져오면 늦다. 게이트웨이를 처음
해석하는 응답이 도착하는 시점에 이웃 항목은 아직 미완성이라, 보호 기록은
그 다음 패킷에서야 잡히고 그 사이는 무방비가 된다.

검증
====

사칭은 즉석에서 판정하지 않는다. 검증하는 동안 갱신은 계속 거부되므로
기다린다고 잃는 것은 없다::

  1초 간격으로 3회:
     보호 대상 앞으로만, 그리고 사칭자 앞으로만
     게이트웨이 주소를 묻는 유니캐스트 ARP 요청을 보낸다

유니캐스트가 핵심이다. 스위치는 한 하드웨어 주소 앞으로 온 프레임을 그
주소가 붙은 포트로만 내보내므로 다른 사람은 그 질문을 보지 못한다.

응답은 그 프로브 후 ``ARP_PROBE_WINDOW`` 안에 이 컴퓨터로 돌아온 것만,
프로브당 하나만 센다.

=================  =================================  ==========================
결과               뜻                                 처리
=================  =================================  ==========================
둘 다 응답         게이트웨이가 살아있는데 남이 그    공격, 사칭자를 차단한다
                   주소를 주장하고 있다
사칭자만 응답      보호 대상이 사라졌다               교체,
                                                      allow_gw_hwaddr_change
                                                      가 켜져 있을 때만 수용
사칭자 무응답      그 패킷이 남의 주소를 적었다       아무도 차단하지 않는다
=================  =================================  ==========================

보호 대상은 1회, 사칭자는 3회 중 2회 답해야 한다.

두 근거의 성격이 다르다.

- **보호 대상의 응답은 위조로 없앨 수 없다.** 살아있는 게이트웨이가 자기
  앞으로 온 요청에 답하는 것을 링크 위에서 막을 방법이 없다. 그래서
  공격자는 게이트웨이를 죽은 것처럼 보이게 만들 수 없고, 그것이 답하고
  있는 한 교체 판정에 도달할 수 없다.

- **사칭자의 응답은 만들어낼 수 있다.** `한계`_ 를 보라.

sysfs
=====

``/sys/kernel/arp_project/``

여기 있는 것은 전부 시스템 전역 설정이다. 인터페이스별도, 네트워크
네임스페이스별도 아니다. 기억하는 내용인 보호 대상과 차단 목록만 장치별로
나뉜다.

스위치
------

============================  ======  =====================================
파일                          기본값  뜻
============================  ======  =====================================
arp_project_enable                 1  전체 on/off
print_arp_info                     0  모든 ARP 패킷을 로그에 덤프
ignore_gw_update_by_request        1  게이트웨이를 옮기려는 request 를 버림
ignore_gw_update_by_reply          1  게이트웨이를 옮기려는 reply 를 버림
ignore_proxy_arp                   0  proxy ARP request 를 통째로 버림
allow_gw_hwaddr_change             0  옛 게이트웨이가 사라진 것이 확인되면
                                      새 주소를 받아들일지
attacker_timeout                   0  차단 유지 초, 0 은 손으로 풀 때까지
============================  ======  =====================================

``ignore_proxy_arp`` 기본값이 휴대폰 커널과 다르다. 라우터나 컨테이너
호스트에서 proxy ARP 는 정상 기능이다.

상태
----

========================  ======  ==================================
파일                      권한    내용
========================  ======  ==================================
protected_gw_hwaddr         0444  ifindex, 게이트웨이 주소, 보호 중인
                                  하드웨어 주소를 한 줄씩. 게이트웨이
                                  8개까지
alt_gw_hwaddr               0444  게이트웨이마다 추가로 받아들인
                                  포트를 같은 형식으로. 게이트웨이당
                                  8개까지
detected_attacker_hwaddr    0444  차단된 호스트의 ifindex 와 하드웨어
                                  주소를 한 줄씩. 장치당 16개까지,
                                  넘치면 오래된 것부터 밀림
clear_gw_hwaddr             0200  1 을 쓰면 보호 기록을 지우고 다시
                                  학습한다
clear_attacker_hwaddr       0200  1 을 쓰면 차단을 전부 해제한다
arp_project_version         0444  버전
how_to_use                  0444  이 문서의 요약 (영문)
========================  ======  ==================================

clear 로 시작하는 두 파일은 하는 일이 다르다.
``clear_attacker_hwaddr`` 는 "이 놈은 공격자다" 를 취소한다.
``clear_gw_hwaddr`` 는 "게이트웨이는 이 주소다" 를 취소하는데, 공유기를
실제로 교체했을 때와 부팅 시점에 이미 공격당하고 있던 경우에 필요하다.

쓰는 법
=======

::

  # 무엇을 지키고 있나
  cat /sys/kernel/arp_project/protected_gw_hwaddr
  # 2 192.168.0.1 aa:bb:cc:dd:ee:ff

  # 무엇이 차단됐나
  cat /sys/kernel/arp_project/detected_attacker_hwaddr

  # 무엇을 판정했나
  dmesg | grep arp_project

  # 공유기를 실제로 교체했다
  echo 1 > /sys/kernel/arp_project/clear_gw_hwaddr

  # 잘못 막힌 호스트를 풀어준다
  echo 1 > /sys/kernel/arp_project/clear_attacker_hwaddr

한계
====

전부 ARP 계층에서는 닫을 수 없는 것들이다.

**첫 학습을 믿는다.** 부팅 시점에 이미 공격당하고 있으면 공격자가 보호
대상이 된다. ``protected_gw_hwaddr`` 로 무엇이 잡혔는지 확인할 수 있고
``clear_gw_hwaddr`` 가 유일한 대처다.

**3자 누명이 완전히 막히지는 않는다.** 차단의 근거인 "사칭자가 프로브에
답했다" 는 만들어낼 수 있다. ARP 응답에는 어느 요청에 대한 답인지 표시할
칸이 없어서, 도착한 시각 말고는 요청과 묶을 방법이 없다. 이 코드로 실측한
값이다.

=================  ==============  ==================
위조 응답 속도     누명 성공        게이트웨이 보호
=================  ==============  ==================
초당 2개           10회 중 0회      유지
초당 50개          5회 중 5회       유지
=================  ==============  ==================

두 경우 모두 게이트웨이 보호는 유지됐고, 그것이 실제로 값어치 있는
보증이다. 차단 목록이 아니라 ``protected_gw_hwaddr`` 가 그 보증이다.
프로브는 사칭 패킷을 받아서 나가므로, 느리게 뿌리면 다음 패킷이 창 밖에
떨어진다.

**게이트웨이를 침묵시킬 수 있는 공격자** 는 교체 판정에 도달한다. 다만
``allow_gw_hwaddr_change`` 가 꺼져 있으면 그래도 거부하고 로그만 남긴다.

**크기.** 장치당 게이트웨이 8개, 차단 16개다. 앞의 것을 넘으면 그 뒤
게이트웨이는 로그에 경고를 남기고 무방비가 되고, 뒤의 것을 넘으면 가장
오래된 항목이 밀려난다.

**하드웨어 주소를 바꿔가며 오는 공격자** 는 차단 목록만 채운다. 지속되는
방어는 보호 대상 쪽이다.
